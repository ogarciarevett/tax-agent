# Agent Operating Contract — tax-agent

## Source-of-truth convention (READ FIRST)
- The ONLY hand-edited spec files are `.ai/context.md` (the project contract) and
  `.ai/pipeline.md` (the graph-orchestrated loop lifecycle). Everything else at the repo root is
  GENERATED by `sh scripts/sync-ai-docs.sh` (a dependency-free POSIX shell script) — NEVER
  edit a generated file: your edit is overwritten on the next sync.
- The per-tool mirrors/adapters (`.claude/`, `.gemini/`, `.opencode/`, `.cursor/`,
  `.ai/generated/`; Codex may also create `.agents/` and `.codex/agents/`) are
  **gitignored / local-only** — the repo carries NO duplicated skill/agent/command copies, only
  the single `.ai/` source. Regenerate the sync-owned mirrors with `sh scripts/install.sh` (or
  the sync script) once per clone, or your tools see zero skills. Tool-owned adapters may be
  recreated by the CLI at startup. The ONLY generated files committed are the root contract
  entries `AGENTS.md` / `CLAUDE.md` / `GEMINI.md` — kept so the repo stays readable on GitHub
  and the contract loads without a build step; the pre-commit hook gates only those.
- How each entry file is produced:
  - `AGENTS.md` and `.ai/generated/rules.mdc` INLINE the full contract — readable
    everywhere (GitHub web view, Codex, any tool without `@`-import support). `AGENTS.md` is the
    committed canonical copy; `.ai/generated/rules.mdc` is its gitignored local twin.
  - `CLAUDE.md` and `GEMINI.md` are thin stubs that just `@`-import `AGENTS.md` (the committed
    canonical inline, which itself ends with the `@.ai/memory.md` reference) — Claude Code and
    Gemini CLI resolve the import, so the contract + memory ride along through one canonical entry
    and are NOT duplicated into them.
  - `.cursor/rules/00-context.mdc` is a (gitignored, regenerated) symlink → `.ai/generated/rules.mdc`.
    Add another IDE by symlinking its rules path to that artifact — no script change needed.
  - opencode reads `.ai/context.md` + `.ai/pipeline.md` + `.ai/memory.md` directly.
  - Commands (`.ai/commands/`), subagents (`.ai/agents/`), skills (`.ai/skills/`), and references
    (`.ai/references/`) are hand-edited sources too; the sync script fans commands/agents/skills
    into every tool's (gitignored, local-only) mirror dir. References are read by path and are NOT
    fanned out. A skill may use a Claude-Code-only accelerant internally (e.g. `/graphify`) as long
    as it degrades gracefully for the other CLIs — see the `evolve` skill for the pattern. Keep
    `.ai/` language-agnostic: no per-tool runtime artifacts live here. Codex-local adapters such as
    `.agents/` and `.codex/agents/` are projections of `.ai/` for that runtime, not a second source.
    Parallel fan-out uses each tool's native sub-agents (see `.ai/pipeline.md`), not committed scripts.
- OPTIONAL per-stage model routing: a command or subagent may add a `model:` key to its
  frontmatter (e.g. `model: openrouter/anthropic/claude-sonnet-4`) to pin the model for that
  stage. **opencode** honors it on both `.opencode/commands/` and `.opencode/agents/`; it degrades
  gracefully elsewhere (the Gemini transform keeps only `description` + body, and Claude Code /
  Codex ignore unknown keys). Keep the COMMITTED `.ai/` sources vendor-neutral — never hardcode a
  provider's model id into a template command; routing is an opt-in each project sets for its own
  opencode runtime. See the README's "Per-stage model routing" recipe.
- All spec/planning/acceptance artifacts live under `.ai/specs/`. PROJECT-LEVEL docs use the
  numeric scheme (`00-requirements.md`, `01-spec.md`, `02-plan.md`, `03-review.md`,
  `97-evolution.md` (from `/evolve`), `98-nice-to-haves.md`, `99-acceptance.md`). PER-TASK specs
  use a letter+number id (`A1-spec.md`, `B4-spec.md`, `P1-spec.md`, …) and are saved IN THE REPO
  ONLY when the repo has no external backlog — see "Task identity & spec source" below. Each task's
  COMPILED EXECUTION GRAPH lives at `.ai/specs/task-graphs/<id>.json` and is validated by
  `node scripts/validate-task-graph.mjs`.
- Repo-root files: `AGENTS.md` / `CLAUDE.md` / `GEMINI.md` are GENERATED; `README.md` and
  `EVALS.md` are HAND-EDITED (human-facing catalogues, not part of the sync).
- Memory (`.ai/memory.md`) is LOCAL and gitignored — see the Memory protocol below.
- To change a convention: edit `.ai/context.md` / `.ai/pipeline.md`, run
  `sh scripts/sync-ai-docs.sh`, and reflect it in `.ai/specs/01-spec.md`. At the end of every `/build`
  node, confirm the sources still match reality; if they drifted, fix and re-sync in the same
  node. A PR that changes a convention without re-running the sync (leaving generated
  docs stale) is incomplete.

## Project
**Tax Agent — Financial Intelligence Graph.** A reusable, **multi-user and multi-household**
financial intelligence platform. It combines deterministic financial accounting over append-only
financial facts with budgeting and monthly cash flow, debt planning, tax reserves and payment
schedules, goal dependencies, mortgage readiness, multi-currency accounts, fiat and crypto assets,
document ingestion, hybrid lexical + vector retrieval, graph-based financial relationships, closed
financial feedback loops, auditable AI recommendations, and evidence-backed explanations.

The platform must support arbitrary users, households, household members, accounts, institutions,
liabilities, assets, jurisdictions, currencies, financial goals, tax calendars, risk tolerances,
and recurring obligations. The initial owner's real financial data may later be represented as
private seed/demo data; **it must never become universal business logic**.

Dominant constraint: **financial correctness and auditability**. Every figure traces to a source
document or a cited rule; personal financial data (PII) stays under the user's control.

**Status: PIPELINE / BOOTSTRAP PHASE.** The platform above is NOT implemented. What exists today is
the operating contract, the pipeline, and the Legacy CLI (v0) below.

## Legacy CLI (v0) — frozen, pre-pivot
`src/**` contains a **shipped, tested, single-user, Spain-only local-first CLI** (Node 22 · pnpm ·
better-sqlite3 · opentui · local LLM CLI subprocesses) delivering `interview`, `scan`, and `report`.
Epics A1 and B0–B7 are complete and green.

- It is **frozen**. It is NOT governed by the locked stack below and must not be "migrated in place".
- It is **not deleted**. It is working, tested code and the reference implementation for two
  constraints the new platform inherits: integer-cents money arithmetic and rule-id/document-id
  provenance on every emitted figure (`src/countries/es/report.ts`).
- Phase 1 ports its durable assets — the cited Spain rules (`src/countries/es/rules.ts`), the
  integer-cents money model, and the `figure(label, cents, ruleIds)` provenance pattern — into the
  new jurisdiction plugin. The port is additive; the legacy tree is retired only once the port is
  verified.
- Its own gates (`pnpm exec tsc --noEmit`, `pnpm exec biome check`, `pnpm test`) remain part of the
  Definition of Done, so contract work cannot silently break it.

## Stack (LOCKED — do not relitigate)
TypeScript 7 · Bun · Next.js App Router · React Server Components by default · PostgreSQL as the
primary datastore · pgvector for embedding storage · PostgreSQL lexical retrieval · hybrid lexical +
vector retrieval with reciprocal-rank fusion · Drizzle ORM · Zod · shadcn/ui · Tailwind CSS ·
OpenTelemetry · structured logging · Vitest · Playwright · Docker Compose · committed SQL migrations.

### PostgreSQL version posture
- **PostgreSQL 19 is the target development and compatibility version.**
- Until PostgreSQL 19 reaches general availability and passes compatibility validation, **production
  posture remains the latest supported PostgreSQL 18 release**.
- This contract must **not** describe a PostgreSQL beta as production-ready. As of 2026-08-02,
  PostgreSQL 19 is in **Beta 2** (released 2026-07-16) and is NOT generally available.
- During the transition, migrations and core queries are evaluated against **both** versions.
- Recorded in `docs/adr/0004-postgresql-19-version-posture.md`. Once PG19 is GA, the decision may be
  revisited through `/evolve` and a human-reviewed ADR update.

### Hybrid retrieval rule
- Do **not** call PostgreSQL `ts_rank` "BM25" unless it actually is BM25.
- The concrete lexical-ranking implementation must be identified, benchmarked, and documented in an
  ADR **before** retrieval production code begins.
- pgvector is the vector store. Do **not** add a separate vector database by default.
- Do **not** add Elasticsearch, OpenSearch, or another search service without an ADR and evidence.

### Out of bounds unless a later ADR explicitly approves it
JavaScript floating-point money calculations · a dedicated graph database in the initial phases ·
an external vector database · LLM-generated SQL executed without a controlled query layer · LLM
mutation of financial facts · production use of prerelease database software without explicit human
approval · hidden background financial actions · multi-tenant access without explicit authorization
filters · hand-edited generated agent files.

## The four graphs (never conflate them)
1. **Repository reality graph** — files, modules, imports, schemas, interfaces, commands, skills,
   tests. Derived from repository reality; cacheable; regenerable; **never the normative source of
   project requirements**. May be built with `/graphify` when available, with a direct-scan
   fallback. Graphify output is NOT the financial domain graph. Consumed by `/map` and `/evolve`.
2. **Task execution graph** — one task as a dependency DAG at `.ai/specs/task-graphs/<id>.json`.
   Determines readiness, critical path, and safe parallelism; associates each implementation node
   with invariants and evidence. Compiled from an approved task spec; committed; acyclic;
   human- and machine-readable; updated only by the lead/integrator; **references its normative
   spec and may never override it**. Schema: `.ai/references/task-graph-schema.md`.
3. **Financial domain graph** — financial relationships, dependencies, blockers, enablers,
   exposures, provenance, and explanations inside the product. Stored in PostgreSQL initially;
   separate from the ledger; multi-tenant; versioned; provenance-aware. **NOT implemented in P0.**
   **The graph must never replace the ledger.**
4. **Evidence graph** — proves completion via `requirement → behavior → implementation → test →
   passing evidence`. Every verified criterion needs a complete path. Implementation without a
   requirement or invariant is *unexplained scope*; a requirement without passing evidence is
   *not verified*. Stored through task reports and `.ai/specs/99-acceptance.md`.
   Schema: `.ai/references/evidence-graph.md`.

The **ledger** is the source of financial truth. **RAG** provides documentary evidence and
historical context and must **never** be the authoritative source of current financial balances.

## Financial correctness constraints (non-negotiable)
1. No loss or silent mutation of financial facts.
2. Deterministic monetary calculations.
3. No floating-point money arithmetic.
4. Explicit currency on every monetary value.
5. Household and tenant isolation.
6. Provenance for every imported fact.
7. No LLM-only financial arithmetic.
8. No LLM-initiated transfer, trade, or debt payment.
9. Explicit separation between actual, planned, forecast, simulated, and recommended.
10. Immutable scenario inputs.
11. Reproducible recommendations.
12. Evidence and assumptions attached to every financially material recommendation.
13. No stablecoin represented as equivalent to a protected bank deposit.
14. No tax estimate represented as professional tax advice.

## Definition of Done (all must pass)
Runnable feature evals green (`pnpm eval` — every feature accounts for UI, backend log, DB and
output; see `EVALS.md`) · Tests green + coverage ≥ 80% **over `src/**`** (`pnpm test`; repo machinery under `scripts/` has
its own runner, `pnpm test:graph`, and does not contribute to that number) · typecheck clean
(`pnpm exec tsc --noEmit`) · linter/formatter clean (`pnpm exec biome check`) · task graph valid
(`node scripts/validate-task-graph.mjs .ai/specs/task-graphs/<id>.json`) · every external input
validated with Zod at the boundary · no secrets or PII in logs · new errors recorded in
`.ai/memory.md` · generated agent docs in sync (`sh scripts/sync-ai-docs.sh`, enforced by the
pre-commit hook) · each task ships an Honest Implementation Report — no ✅ without pasted evidence.

Project gates: every monetary calculation is covered by a unit test against known fixtures ·
jurisdiction-specific logic lives behind the per-jurisdiction module (never hardcoded into shared
code) · no figure is emitted without a traceable source (document or cited rule) · every node's
actual write set matches its declared `write_set`, checked by
`validate-task-graph.mjs --reconcile --node <id>` at `/build` step 8 (**run by the lead, not by a
hook or CI** — there is no CI in this repo yet) · no node is `VERIFIED` without a complete evidence
path.

## Hard rules
NEVER push / open PRs / create remote branches / add collaborators / deploy.
Commit locally; the human pushes. NEVER commit `.env` or any secret.
Project-specific:
- Personal financial data / PII / documents stay under the user's control — never commit the `data/`
  dir or any document, and never log PII.
- Never fabricate a financial figure — every number traces to a source document or a cited rule.
- Never let an LLM perform financial arithmetic on its own, mutate a financial fact, or initiate a
  transfer, trade, or payment.
- Start with one jurisdiction but never hardcode it into shared code — jurisdiction rules live
  behind the per-jurisdiction module so a second jurisdiction is additive.
- Multi-tenant reads and writes always carry an explicit authorization filter.
- `src/**` is frozen Legacy v0 (see above) — do not extend it, do not migrate it in place.
- ONE WRITER during contract/bootstrap work. Parallel implementation nodes are permitted ONLY when
  no dependency path exists between them, write sets are disjoint, schema ownership does not
  overlap, shared invariants are not modified concurrently, each writer uses a **separate git
  worktree**, and the lead integrates and reruns all global gates.

## Task identity & spec source (the pipeline runs PER TASK)
The lifecycle in `.ai/pipeline.md` runs once PER TASK. Before starting, fix the task's identity and
decide where its spec lives:

- **External backlog (Linear or GitHub Projects) → the tracker is the source of truth.** The task id
  is the EXTERNAL id (e.g. `ENG-421`, `#123`) and the ticket body holds the spec. Do NOT create a
  local `<id>-spec.md`. Read the ticket and cite its id in the spec summary, task graph
  `spec_source`, commits, and acceptance.
- **No external backlog → the spec is saved IN THE REPO** as `.ai/specs/<id>-spec.md` with a
  letter+number id (letter = epic, number = task within it). Epics in use: `A` (legacy interview),
  `B` (legacy scan/report), `P` (pipeline/platform contract). `.ai/specs/02-plan.md` is the local
  backlog/index of every task id.
- **Either way**, the compiled execution graph is committed at `.ai/specs/task-graphs/<id>.json`.
- **Source precedence:** (1) human-approved external ticket → (2) `.ai/specs/<id>-spec.md` →
  (3) `.ai/specs/01-spec.md` architecture → (4) the compiled task graph → (5) execution status and
  reports. **The compiled task graph may never override its normative spec.** On disagreement: stop,
  mark the node `GRAPH_DRIFT`, reconcile, and obtain approval when behavior changes.
- **Detection (vendor-neutral):** GitHub Projects → `gh project list` returns ≥ 1 project. Linear →
  a Linear MCP server is configured in the repo's `.mcp.json`, `LINEAR_API_KEY` is set, or
  branches/commits use the `eng-123` key style. A user-level connector that the repo does not
  configure does NOT count. If detection is inconclusive (e.g. `gh` lacks `read:project` scope),
  say so explicitly and default to the local scheme. `/spec` states which source it detected —
  and how — before writing anything.

## Consensus review (mandatory reviewers — NOT a generic 2-of-3)
A simple majority may never override a correctness proof failure.

- **Pipeline-contract changes** (anything under `.ai/`, `scripts/`, `.githooks/`) require:
  `code-reviewer` · `graph-consistency-reviewer` · `loop-correctness-reviewer` ·
  `security-auditor`.
- **Financially material product logic** requires: `code-reviewer` · `financial-domain-reviewer` ·
  `ledger-invariant-reviewer` · `security-auditor` · plus `graph-consistency-reviewer` when graph
  behavior changes and `loop-correctness-reviewer` when workflow behavior changes.
- **Approval rule:** no unresolved critical finding · no unresolved high-severity financial,
  security, invariant, graph, or loop finding · **every mandatory correctness reviewer approves**.
- Reviewer opinion is not test evidence. A reviewer's ✅ never substitutes for pasted output.

## Authoring conventions
- **Personas are single-role specialists.** Never create a meta-orchestrator, a router, a persona
  that invokes another persona, or a persona that owns the whole pipeline. Slash commands, the
  human, and the external multiplexer lead perform orchestration. No nested orchestration.
- **Add a command only when it owns a distinct state transition or artifact.** Renaming an existing
  step is not a reason for a new command.
- **Skill structure.** Most skills follow the house template (Overview → When to Use with an inline
  `**When NOT to use:**` → process steps → output template → Common Rationalizations → Red Flags →
  Verification). Skills that govern **financially material or contract-critical** work EXTEND that
  template with explicit `Inputs`, `Non-goals`, `Invariants`, `Failure modes`, and `Recovery`
  sections. This deviation is deliberate: burying an invariant in a Red Flags bullet is how it gets
  skipped. The four graph/loop/hardness skills use the extended form.

## Honesty protocol — Honest Implementation Metric (anti-overclaim)
LLMs tend to over-report success ("done ✅") even when a step was skipped, stubbed, or never
actually run. This contract forbids that. Every task ends with an **Honest Implementation
Report**; `/build` emits it per node and `/acceptance` aggregates it. Rules (apply on every CLI):

- **Per acceptance criterion, a status backed by PASTED evidence:** ✅ verified · ⚠️ partial ·
  🔧 stubbed/mocked · ❌ not done · 🚫 blocked. A status is ✅ ONLY if the actual output proving it
  is pasted inline — a test run, build/typecheck log, runtime output, or a `file:line` pointer.
  No evidence → it is NOT ✅.
- **Honest Implementation Metric (the number):** `verified ✅ criteria ÷ total criteria`, as a
  0–100% score reported per task. A task is "done" only at 100% with evidence on every row.
- **Two lists that are NEVER omitted:** *Unverified* — anything asserted but not proven by pasted
  output ("should work", assumptions); *Could-not-do* — anything you could not perform here
  (missing creds, no network, env limits, ambiguous spec), stated plainly.
- **Agent/pane status is not proof.** An external multiplexer reporting `idle`, `done`, or
  `unknown` proves nothing about correctness. Evidence is files, diffs, and command output.
- **Under-claiming is fine; over-claiming is a contract violation.** Reporting ⚠️/❌/🚫 with a
  clear reason is correct and expected. NEVER invent passing output, NEVER claim a test/build/run
  you did not execute, NEVER mark ✅ just to look finished. When unsure, mark ⚠️ and say why. This
  metric is graded on honesty, not on the score being high.

## Memory protocol (shared across Claude Code, Codex, Gemini, opencode)
- `.ai/memory.md` is a LOCAL, per-developer working log — it is **gitignored**, not
  committed. Seed it from the committed template `.ai/memory.example.md` (this happens
  automatically on `sh scripts/sync-ai-docs.sh`).
- It is referenced (`@.ai/memory.md`), never inlined into committed files — that would
  leak local notes into git and churn the generated docs on every append.
- DURABLE, team-facing decisions do NOT go here. They go in the commit message and/or a
  short ADR under `docs/adr/` — reviewed and committed. Memory is for ephemeral,
  per-dev working notes only.
- APPEND, never rewrite. Keep entries terse, newest at the bottom of `## Log`. Shapes:
  - `### [YYYY-MM-DD] build-error` — `symptom → root cause → fix`.
  - `### [YYYY-MM-DD] gotcha` — environment/library quirk found the hard way.
- NEVER write a secret (private keys, `.env` values, signed payloads, bearer tokens) — even
  though it is local, the example is committed and the habit leaks.
